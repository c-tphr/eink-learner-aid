# tools/device: the guarded Picco flash session tool

This folder is what the owner runs at their Windows PC in the device session (plan section 10): identify the Picco, back it up, flash the two-slot firmware, record the serial log, and restore the backup if anything goes wrong. It replaces Onyx's bootloader and partition table, which only the backup can bring back, so the tool is built around one rule: **nothing is written unless two identical full backups exist, and then only the four planned images, at their four allowed offsets, byte for byte.**

The owner runs one script, `session.ps1`. Everything that decides what may be written lives in a Python package, `piccoflash`, so it can be unit-tested in Linux against a fake device. The owner's checklist (`docs/DEVICE_SESSION.md`) is task D6; the [hand-off list](#hand-off-to-the-checklist-task-d6) below gives it every prompt, phrase, output and stop condition.

## Commands

```
.\session.ps1 setup                       # prepare the private Python only
.\session.ps1 identify                    # read-only
.\session.ps1 backup                      # read-only
.\session.ps1 plan                        # show and verify kit\flash-plan.json (no device)
.\session.ps1 flash [-DryRun]             # the only destructive command besides restore
.\session.ps1 monitor [-Reset]            # serial log until Ctrl+C
.\session.ps1 restore <backup.bin> [-DryRun]
.\session.ps1 ports                       # list serial ports
common options: -Port COMn  -DryRun  -Plan <kit folder or flash-plan.json>  -WorkDir <folder>
```

If Windows refuses to run the script ("running scripts is disabled on this system", or the file is marked as downloaded), run it through PowerShell with a one-off bypass. This changes no setting on the PC:

```
powershell -ExecutionPolicy Bypass -File .\session.ps1 identify
```

The same commands exist as `python -m piccoflash <command>` with `--dry-run`, `--port`, `--work-dir`, `--plan`, plus `make-plan` for whoever builds the kit. Exit codes:

| Code | Meaning |
| --- | --- |
| 0 | OK |
| 1 | STOP or refused. Nothing was written. |
| 2 | Command-line mistake |
| 3 | identify: the Picco already has the two-slot table |
| 4 | The chip could not be reached. Nothing was written. |
| 5 | flash started writing and did not finish and verify: run `restore` |
| 6 | restore did not finish and verify: run `restore` again |
| 10, 11, 12 | session.ps1 set-up failed (unsupported PC, download or hash failure, pip failure). The device was not touched. |

## Architecture

```
session.ps1  (thin: pinned Python, pinned packages, passes options through)
   |
python -m piccoflash <command>          cli.py
   |-- identify.py   read-only checks, verdict (pure evaluate())
   |-- backup.py     two full reads, compare, keep, acknowledgement
   |-- flash.py      preconditions, typed phrase, re-identify, ordered guarded writes
   |-- restore.py    guarded full write at 0x0, full read-back
   |-- monitor.py    serial log (pyserial only, sends no data)
   |-- plan.py       flash-plan.json: validate, verify, make-plan, print
   |
   |-- guard.py      THE POLICY: pure, no I/O, no override. approve_*() -> ApprovedWrite; recheck()
   |
   |-- device.py     Device interface: connect, chip_info, security_info, read, write(ApprovedWrite), hard_reset
         |-- esptool_device.py   real chip: pinned esptool 5.6.0, Python API, calls from esptool_calls.py
         |-- tests/fakedevice.py in-memory 16 MB ESP32-S3 with injectable faults
```

`Device.write` accepts only a `guard.ApprovedWrite`, which only the guard can create (a module-private seal). Every implementation calls `guard.recheck()` on it immediately before writing: the seal, the SHA-256 of the exact bytes, and the whole policy are checked again. `flash` reads each image file again just before its write and has the guard approve those bytes, so a file changed after the plan was verified is refused.

### Why esptool's Python API and not its command line

The guard approves a `bytes` object and the driver hands that same object to `esptool.cmds.write_flash`. Nothing re-reads a file between the check and the write. Identify decisions also use esptool's structured results (the `GET_SECURITY_INFO` dictionary, eFuse reads, the flash JEDEC id) instead of parsing printed text. Each call is described once, as data, in `esptool_calls.py`. `--dry-run` prints those descriptions, the log records them with the equivalent esptool 5.x command line, and the driver executes exactly the described call. A test binds every described call to the real esptool function signatures.

### esptool 5.6.0: options relied on

Checked against the esptool documentation at docs.espressif.com ("Basic Commands", "Advanced Options", "Flasher Stub", "Embedding into Custom Scripts") and the 5.6.0 source.

| Option | Why |
| --- | --- |
| `detect_chip(port, baud=115200, connect_mode="default-reset", connect_attempts=7)` (CLI `--before default-reset`) | esptool recognises the ESP32-S3 USB-Serial/JTAG peripheral (USB id 303A:1001) and uses its reset sequence to enter ROM download mode. The baud rate has no effect on USB-Serial/JTAG speed and is never changed. |
| stub flasher on (`run_stub`, no `--no-stub`) | Runs in RAM only. Needed for a practical 16 MB read (the ROM-only read is very slow), compressed writes and the post-write MD5 check. Not used on a chip in secure download mode (identify stops there). |
| `attach_flash` | Required by esptool before flash operations. |
| `write_flash(..., flash_mode="keep", flash_freq="keep", flash_size="keep")` | esptool must not patch the bootloader header, so the bytes in flash equal the hashed file. A test runs esptool's own header code to show `keep` leaves the image unchanged and a setting would change it. |
| `erase_all=False, encrypt=False, force=False` | Erase only the sectors written; never encrypt; never bypass esptool's own checks (e.g. image/chip compatibility at 0x0). |
| no `skip_flashed`, `diff_with` | Always write the whole image. |
| `read_flash(..., flash_size="keep")` | Read by address with the stub. |
| `reset_chip(esp, "hard-reset")` | Only after a command finished successfully. After a failed write the chip is left in the loader so `restore` can reconnect. esptool notes that on USB-Serial/JTAG this is a core reset that does not re-sample the strapping pins. |
| no esptool config file, no `ESPTOOL_*` variables | The driver refuses to run if an `esptool.cfg`/`setup.cfg`/`tox.ini` with an `[esptool]` section is active, and removes `ESPTOOL_*` and `ESP_IDE_WS` from its own environment, so nothing on the PC can change reset sequences or timeouts, or make esptool open a network connection. |
| `esptool.__version__ == "5.6.0"` | The driver refuses any other version. |

esptool 5.x renamed the commands with hyphens (`write-flash`, `read-flash`); 4.x used underscores. esptool is GPL-2.0-or-later. piccoflash imports and calls it as a library; no esptool source is copied into this MIT-licensed repository.

## The guard policy

Hard-coded in `guard.py` for this device. The plan file cannot widen it, and there is no `--force`, offset or skip option (a test checks the parser).

**flash**: exactly these four images, each once, nothing else:

| Role | File | Offset | Region (writes must stay inside, after rounding to 4 KiB sectors) | Length | Content check |
| --- | --- | --- | --- | --- | --- |
| bootloader | `bootloader.bin` | 0x0 | 0x0000-0x7FFF | 24 .. 0x7FFF (< 0x8000) | one ESP image, magic 0xE9, chip id 9 (ESP32-S3), checksum and appended SHA-256 valid, file length equals image length, header DIO / 16MB / 80m, ESP-IDF bootloader description present |
| partition_table | `partitions.bin` | 0x8000 | 0x8000-0x8FFF | exactly 0xC00 | byte-equal to our two-slot table as gen_esp32part writes it (32-byte entries, magic 0x50AA, MD5 entry 0xEBEB); SHA-256 `0d3fad51...` as measured in spike S3 |
| boot_app0 | `boot_app0.bin` | 0x15000 | 0x15000-0x16FFF | exactly 0x2000 | the Arduino 3.3.11 file, SHA-256 `f94c5d78...`; selects slot app0 |
| app | `firmware.bin` | 0x20000 | 0x20000-0x7FFFFF | 24 .. 0x7E0000 | one ESP image as above, chip id 9, ESP-IDF application description in the first segment |

Refused by name: anything touching the stock NVS 0x9000-0x14FFF, and 0xE000 (the framework's default `boot_app0` offset, inside NVS). Also refused: a fifth image, a missing image, duplicate roles or offsets, overlaps, file names like `*factory*`/`*merged*`, a file whose SHA-256 differs from the plan, any partition table other than ours (the stock table is named as such).

**restore**: exactly one image, 16,777,216 bytes at 0x0, whose SHA-256 equals the hash recorded when the backup was taken (the `.json` record beside the `.bin`), from a backup recorded as verified.

## Write order and failure analysis

`flash` writes **app, then boot_app0, then partition table, then bootloader**, reads each region back and compares its SHA-256 before going on, and stops at the first failure (later regions are not written; the restore command is printed; exit 5).

Why this order: every intermediate state either still boots Onyx, boots our app, or boots nothing at all. No state runs Onyx's code (its app or its `safeboot` recovery app) under a foreign bootloader or table, which could do things nobody can predict. The bootloader, the change most likely to be incompatible with this unit (plan section 13), is written last and is the smallest write (about 18 KB, under a second), so the window with a half-written bootloader is as short as possible. The opposite order (bootloader first) would boot Onyx's app and `safeboot` under the Arduino bootloader and then under our table.

What makes recovery possible in every case: the ESP32-S3's first-stage bootloader is in mask ROM and cannot be erased. Its download mode is entered through the USB-Serial/JTAG reset whatever the flash holds, provided the chip is not running an app that has taken the USB port away (Onyx and our firmware both keep it, see the unknowns below), and no eFuse disables it (identify checks).

| Interrupted (power, cable, crash) | Flash then holds | What the chip does on the next power-up (expected) | Recovery |
| --- | --- | --- | --- |
| before step 1 | stock | Onyx | nothing to do |
| during step 1 (app, 0x20000, several MB), before the write reaches 0xE0000 | Onyx bootloader, stock table and otadata; `safeboot` partly erased; Onyx app intact | Onyx bootloader boots the Onyx app as before | `restore` (to get `safeboot` back) |
| during step 1, after 0xE0000 | as above but the Onyx app header is overwritten | Onyx bootloader finds no valid app (Onyx app and factory both invalid): nothing boots; ROM download mode reachable | `restore` |
| after step 1 | our app at 0x20000 (the stock `safeboot` slot), stock table | Onyx bootloader: ota_0 at 0xE0000 invalid, falls back to the factory partition at 0x20000, which is now our app. Our app runs on the stock table: one OTA slot, so updates stay hidden | `restore`, or run `flash` again (identify still sees the stock table, so it re-writes all four) |
| during or after step 2 (otadata, 8 KB) | as above, otadata half or fully ours | Onyx bootloader: no valid ota_0 either way, falls back to our app at 0x20000 | as above |
| during step 3 (table, 4 KB sector) | table sector erased or partial | Onyx bootloader cannot read a table: nothing boots; ROM download mode reachable | `restore` |
| after step 3 | Onyx bootloader, our table and otadata, our app | Onyx bootloader boots app0 (our app) through a standard table | `restore` (flash refuses to run again: identify now says "already converted") |
| during step 4 (bootloader, about 18 KB) | half-written second-stage bootloader | ROM cannot load it: nothing boots; ROM download mode reachable | `restore` |
| after step 4, before or after its read-back | target state | our bootloader and app | done (or `restore` if the read-back failed) |

The "expected" column follows the ESP-IDF bootloader's documented fallback rules; it was not observed on a Picco. Restore never depends on what boots: it only needs ROM download mode.

Erase granularity: esptool erases every 4 KiB sector a write touches (documented in "Basic Commands, Erasing Flash Before Write"). The guard therefore checks the sector-rounded span, the fake device erases the same way, and the end-to-end test checks that each region holds the image, then 0xFF to the end of its last sector, then the untouched stock bytes, and that every byte outside the four spans (including all of NVS) is unchanged.

## What each command checks

**identify** (read-only; resets the chip into download mode, then back to normal): chip type and revision, MAC, features (including in-package PSRAM if the eFuses report it), crystal, flash JEDEC id and detected size, eFuse `FLASH_TYPE`, `GET_SECURITY_INFO` (Secure Boot, `SPI_BOOT_CRYPT_CNT`, secure download mode, download-mode cache restrictions, key purposes, USB disable flag) plus the Secure Boot and flash-encryption eFuse registers as a second source. It reads 0x0+0x8000 (the whole bootloader region, to find a Secure Boot signature block after the image as well as the header), 0x8000+0xC00 (the table) and 0x15000+0x2000 (otadata), and saves `identify-<time>.json` with the three blobs. Verdict:

* **STOP** (exit 1) unless: ESP32-S3; not in secure download mode; flash reports 16MB; `FLASH_TYPE` quad; Secure Boot off; `SPI_BOOT_CRYPT_CNT` zero; download-mode cache access not restricted; no flash-encryption or Secure Boot key purposes burned; the bootloader at 0x0 is a valid unsigned ESP32-S3 image; the table equals `partitions_picco.csv` row for row (an MD5 entry, if present, must be correct).
* **ALREADY_CONVERTED** (exit 3): everything passes but the table is our two-slot table. Decision: `backup` and `flash` refuse such a device; updates go through the SD card (`update.bin`); `restore` still works.
* **PASS** (exit 0): everything passes and the table is stock.

**backup** (read-only): needs a passing identify for the connected MAC in the work folder and re-runs identify. Reads all 16 MB twice into `.read1.bin` and `.read2.bin`, checks each file on disk, compares SHA-256, and also checks that the first 36 KiB equal what identify just read. Equal: keeps `picco-backup-<mac>-<time>.bin` with a `.json` record (hash, size, MAC, chip and security info, tool versions, `verified: true`). Different: keeps both reads, writes `...-MISMATCH.json` listing the differing 64 KiB blocks, marks nothing, exit 1. Then asks the owner to copy the file to a second place and type the last 8 characters of its SHA-256 (3 tries; stored as `owner_ack`; `flash` asks again if it is missing).

**flash**: see the docstring at the top of `flash.py` and the order above. It refuses unless the plan verifies; the work folder has a verified backup whose file is present and still hashes correctly, and a passing identify for its MAC; the backup was confirmed; the owner types the phrase; and, after connecting, the chip has the same MAC, still passes identify with the stock table, and its bootloader and table bytes equal those in the backup.

**restore**: needs the backup's `.json` record (verified, same file name) and a file of exactly 16 MiB with the recorded SHA-256. It does not need identify to pass. After the phrase it checks: ESP32-S3, 16MB, no flash encryption, no secure download mode, and the MAC (a different MAC needs a second phrase). Writes at 0x0 with `keep`, reads all 16 MB back, compares SHA-256, resets.

**monitor**: opens the port with DTR and RTS off (so opening it does not reset the chip), copies everything to `work\serial-<time>.log` and the console until Ctrl+C, and waits for the port to come back when it disappears (USB-Serial/JTAG re-enumerates on every chip reset). It never sends data; `-Reset` pulses the RTS line once.

## How dry run works

`-DryRun` never opens the serial port and never creates a device object. It runs every offline check for real (plan, guard approval of every file's bytes, backup file hash, work-folder preconditions) and prints each device step as the exact esptool call and its command-line equivalent, in order, with the guard's verdict for each write. It ends with `DRY RUN RESULT: READY` (exit 0) or `NOT READY` and the reasons (exit 1). A test asserts the fake device sees zero operations and that the only write offsets printed are the four planned ones. See `examples/dry-run-flash.txt` and `examples/dry-run-restore.txt`.

## The private Python (session.ps1)

* **Python**: CPython 3.13.17 for Windows x64, the Python Software Foundation's `python` package on nuget.org (`https://api.nuget.org/v3-flatcontainer/python/3.13.17/python.3.13.17.nupkg`), SHA-256 `dce409744b088f94c6e37ba41f8100c384c27e029e843237364c602d30d475e5`, pinned in the script. Its SHA-512 matched the `packageHash` in nuget.org's catalog entry. It is the full CPython with pip 26.2.2, unpacked into `.\runtime\py313`; no installer, no registry entries, no PATH change. Why not python.org: www.python.org is not reachable from the cloud sessions, so a hash for its files could not be measured here, and pinning a hash nobody measured is worse than pinning an official package whose hash was measured. If python.org is preferred, the embeddable zip can replace it once someone measures its SHA-256.
* **Packages**: `pip --isolated install --require-hashes --no-deps --no-cache-dir` from `requirements-build.txt` (setuptools 84.2.1) and `requirements.txt` (esptool 5.6.0 and its 16 dependencies, every file hash-pinned). esptool is published only as a source archive, so pip builds it locally with the pinned setuptools and `--no-build-isolation` (no unpinned build downloads). Windows x64 and Linux x86_64 wheels are both listed for compiled packages, so the same file was exercised here.
* The script checks the downloaded package hash before use (a mismatch deletes it and stops), unpacks into a temporary folder and moves it into place, prints python.exe's Authenticode signature, verifies `esptool.__version__`, and records what the runtime was built from; any change to the pins rebuilds it. Python runs with `-E -s` (ignores `PYTHON*` variables and the user site folder).
* Exit 10 (not 64-bit Windows), 11 (download or hash failure), 12 (pip or Python failure). Antivirus: if python.exe is blocked or quarantined, the script says so; allowing the folder is the owner's decision. SmartScreen does not apply to programs started from PowerShell; a "downloaded file" mark on `session.ps1` is handled by the `-ExecutionPolicy Bypass` one-liner.

## How the tests fake the device

`python3 -m pip install -r tools/device/requirements-test.txt`, then `python3 -m pytest tools/device -q -rs` (about 25 s; nothing is skipped).

Two layers:

1. **`tests/fakedevice.py`** implements the `Device` interface on a 16 MB `bytearray` laid out like a stock Picco (synthetic bootloader, stock table, random NVS, otadata, `safeboot`, Onyx app, spiffs). Writes call `guard.recheck`, erase whole sectors, then write. Faults: unreachable, a byte flipped in the Nth full read, write failing part-way at an offset, read-back corruption after a write, disconnect on the Nth read or on any write, a hook that changes kit files mid-flash, and settable identity and eFuses (chip, flash size and type, Secure Boot, crypt count, secure download mode, cache restrictions, key purposes, MAC).
2. **`tests/test_esptool_device.py`** runs the real driver and esptool 5.6.0's own `read_flash`/`write_flash` code (header handling, padding, compression, MD5 verification) against `FakeStubLoader`, an `ESP32S3StubLoader` subclass that replaces only the methods that would talk to the stub over USB. A whole identify, backup, flash and restore session runs through this path.

Synthetic images (`tests/synth.py`) are well-formed ESP32-S3 images; a test has esptool's own parser verify them, and esptool's `merge_bin` makes the `firmware.factory.bin`-style image the guard must refuse.

Covered: every guard rule (each refusal in the issue, plus forged or tampered approvals); a seeded property test (4,000 random write lists and 3,000 random plans) that the guard never approves a byte outside the four regions, computed independently; every identify stop condition; backup mismatch, drift, disconnect and acknowledgement; flash end to end (content check, then restore to the original byte for byte), part-way failure then restore, read-back mismatch, disconnect, device swapped, layout changed, security turned on, file changed mid-flash, wrong phrase, missing backup or acknowledgement; restore refusals (size, hash, record, renamed file, other MAC, unsafe chip), read-back failure and retry; dry run touching nothing; monitor reconnecting and never sending data; port choice; the command line having no bypass flags; the layout constants against `partitions_picco.csv`, the spike CSV and S3's measured hashes.

## What could not be tested here, and why

No device, no Windows. Everything below is untested until the device session (most of it is exercised by `setup` and `identify`, which change nothing):

1. Whether the stock Picco exposes the ESP32-S3 USB-Serial/JTAG port while Onyx runs, and whether esptool's automatic reset into download mode works on it. If not, `identify` fails with exit 4 and changes nothing. No button combination for manual download mode is known; the checklist carries whatever is known.
2. All real esptool-to-chip communication: sync, stub upload, read and write speed and timeouts over USB-Serial/JTAG on Windows, and how long a 16 MB read or write takes.
3. Whether esptool's hard reset returns the Picco to normal operation after identify and backup, and whether our firmware boots after flash (a core reset does not re-sample strapping pins; the device may need its power button).
4. The real eFuse values, `FLASH_TYPE`, `GET_SECURITY_INFO` on this chip revision, the flash JEDEC id, and whether in-package PSRAM is reported (external PSRAM is not visible to esptool).
5. Onyx's real bootloader and table: the identify checks assume a standard ESP-IDF bootloader image (header, checksum, appended SHA-256) and a standard table. An unusual but harmless Onyx bootloader would make identify STOP (safe direction, but it blocks the session).
6. The real D4 images: the content checks (bootloader DIO/16MB/80m header and description, app description, the exact `boot_app0.bin`, the exact table bytes) were checked only on synthetic images built to the documented formats. A real image the guard does not like is refused by `make-plan` (safe direction); D4/A1 must run `make-plan` on the real files.
7. The failure analysis above: ESP-IDF bootloader fallback behaviour on the Onyx bootloader, and what each half-written state actually does on power-up.
8. Windows serial ports: pyserial's port listing and USB ids on Windows, the in-box `usbser` driver, whether the COM number stays the same when the port re-enumerates, and how DTR/RTS behave when monitor opens the port and when `-Reset` pulses it.
9. `session.ps1` under Windows PowerShell 5.1 and PowerShell 7 on Windows: only PowerShell 7.4.6 on Linux was run (see below). Untested on Windows: the download over TLS 1.2 in 5.1, `ZipFile.ExtractToDirectory` in .NET Framework, `Get-AuthenticodeSignature`, execution policy and the downloaded-file mark, long paths, the console showing Python's prompts, Ctrl+C reaching Python in monitor.
10. The private Python on Windows: python.exe starting, pip building esptool from source on Windows, the Windows wheels of cffi, cryptography, PyYAML and websockets importing.
11. Antivirus, SmartScreen, Controlled Folder Access, OneDrive-synced folders (Documents, Desktop) interfering with python.exe or with 16 MB files being written and renamed. Suggest a plain, non-synced folder such as `C:\picco`.
12. Corporate proxies or firewalls blocking api.nuget.org or pypi.org.
13. Python 3.9 compatibility of `piccoflash` is checked statically only (vermin: minimum 3.7); it runs on 3.13 here and in the kit.

PowerShell checks that did run here: PowerShell 7.4.6 (Linux build from the PowerShell GitHub release) parses the script with no errors; PSScriptAnalyzer 1.23.0 with the default rules plus the compatibility rules for Windows PowerShell 5.1 (two Windows builds) and PowerShell 7.0 reports no findings; `flash -DryRun`, `restore -DryRun`, `plan` and `identify -DryRun` run through the script from a folder path with spaces with a stand-in Python; the download, hash check and unpack of the pinned Python package ran (and a wrong pinned hash deleted the file and stopped); a pseudo-terminal test showed Python's prompt reaching the console before any input and the exit code passing through.

| Step | Command | Prompt or phrase | Good outcome | Stop outcome |
| --- | --- | --- | --- | --- |
| Setup (any time before) | `session.ps1 setup` | none | `[session] Private Python ready.` then `piccoflash 1.0.0` | exit 10/11/12 with `[session] STOPPED: ...` |
| Identify | `session.ps1 identify` | none | `RESULT: PASS. This is a stock Picco ...` exit 0 | `RESULT: STOP` and a list (exit 1); `RESULT: ALREADY CONVERTED` (exit 3); `COULD NOT REACH THE PICCO'S CHIP` (exit 4) |
| Backup | `session.ps1 backup` | `When the copy is done, type the LAST 8 characters of the SHA-256 above:` (3 tries) | `BACKUP VERIFIED: both reads are identical.` then `Thank you. The backup is confirmed.` exit 0 | `STOP: THE TWO READS DIFFER` (exit 1: retry with another cable or port); `REFUSED: there is no passing 'identify'` (exit 1) |
| Rehearse | `session.ps1 flash -DryRun` | none | `DRY RUN RESULT: READY` exit 0 | `DRY RUN RESULT: NOT READY` and reasons (exit 1) |
| Flash | `session.ps1 flash` | (the backup confirmation again if it was not given) then `To replace Onyx on this Picco, type exactly:  REPLACE ONYX` | `[1/4] app ... verified` through `[4/4] bootloader ... verified`, `DONE: all four images written and verified.` exit 0 | `Cancelled: the phrase did not match. | First boot | `session.ps1 monitor` (or `-Reset`) | Ctrl+C to stop | serial lines appear; `Serial log saved: ...` | nothing appears: check the port; the log still records the attempt |
| Restore | `session.ps1 restore "<work\picco-backup-...bin>"` | `type exactly:  RESTORE BACKUP`; if the MAC differs also `RESTORE TO A DIFFERENT DEVICE` | `VERIFIED: the whole flash now equals the backup`, `DONE.` exit 0 | `RESTORE DID NOT COMPLETE` (exit 6: run it again, try another cable or port); `REFUSED` (exit 1) |

Other things the checklist should say:

* The identify stop list, in the owner's words: different chip, flash not 16 MB, octal flash, Secure Boot, flash encryption (or burned encryption or Secure Boot keys), secure download mode or restricted download mode, a signed or unreadable bootloader, a partition table that differs from `partitions_picco.csv`. All mean: stop, nothing changed, attach the work folder to the issue.
* identify and backup reset the chip into download mode and back; the Picco's screen may freeze or the Picco may restart while they run. If it stays frozen afterwards, restart it with the power button.
* `backup` takes two full reads; the duration over USB is unknown until the session. Keep the cable still.
* Copy the backup `.bin` and its `.json` together to a second place before flashing.
* Where the files are: `work\identify-*.json` and blobs, `work\picco-backup-*.bin/.json`, `work\*-MISMATCH.json`, `work\flash-result-*.json`, `work\serial-*.log`, `work\logs\<command>-*.log` (everything shown and typed, plus esptool's output and every esptool call). Attach `work\` (without the 16 MB backup, which holds the owner's device data) to the results issue.
* If more than one Espressif device is connected, or none is found, the tool lists the ports and asks for `-Port COMn`; it never guesses.
* Run from a plain folder (for example `C:\picco`), not a OneDrive-synced one, with about 100 MB free.

## Decisions made where the plan was silent

* The logic is Python, the launcher PowerShell (also in the issue's assignment comment).
* esptool's Python API, not its command line (see above); esptool 5.6.0, the latest release at the time.
* The Python comes from nuget.org's official PSF package, not python.org (python.org was unreachable here, so its hash could not be measured).
* `ALREADY_CONVERTED` is its own result; `flash` and `backup` refuse such a device (the safer choice); `restore` does not.
* Dry run never contacts the device, so it can be rehearsed anywhere; readiness of the work folder is reported.
* identify reads the whole 32 KiB bootloader region (not only 4 KiB) to detect a signature block, and stops on any non-zero `SPI_BOOT_CRYPT_CNT` (not only odd), on burned encryption or Secure Boot key purposes, and on restricted download-mode cache access. The USB-disable flag is recorded, not a stop (the tool is talking over USB when it reads it).
* The guard requires the exact known `boot_app0.bin` and the exact table bytes, a DIO/16MB/80m bootloader header, and the ESP-IDF bootloader or application description, and checks sector-rounded spans.
* Write order app, boot_app0, table, bootloader, with read-back after each.
* flash checks that the chip's bootloader and table bytes equal those in the backup, binding the backup to the device it is about to change.
* The chip is reset after identify, backup, a successful flash and a successful restore; never after a failed write.
* A port is chosen automatically only when exactly one Espressif (VID 0x303A) port exists.
* No automatic retries; the owner re-runs a command.
* Phrases: `REPLACE ONYX`, `RESTORE BACKUP`, `RESTORE TO A DIFFERENT DEVICE` (exact, case-sensitive, one attempt).
* `make-plan --expect-offset ROLE=0x...` lets the build cross-check its own offsets (for example from `pio run -e picco_2slot -t envdump`); it can only cause a refusal.
* `flash-plan.json` stores offsets as upper-case hex strings and sizes as integers.

## For whoever builds the kit (D4, A1)

```
python -m piccoflash make-plan --bootloader .pio/build/picco_2slot/bootloader.bin \
    --partitions .pio/build/picco_2slot/partitions.bin \
    --boot-app0 <framework>/tools/partitions/boot_app0.bin \
    --app .pio/build/picco_2slot/firmware.bin \
    --version <version> --build-id <git commit> \
    --expect-offset boot_app0=0x15000 --expect-offset app=0x20000 -o kit
```

Then ship `session.ps1`, `piccoflash/`, `requirements.txt`, `requirements-build.txt` and `kit/` together. To change a pinned package, edit `dev/make_requirements.py`, run it, and update `PINNED_ESPTOOL_VERSION` (and re-check the options above) if esptool changes. Regenerate the examples with `python3 tools/device/tests/make_examples.py`.
